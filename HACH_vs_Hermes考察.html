INTERNAL REPORT v2

hermes-agent を共通基盤とした
HACH連携 vs 自社Hermes構築の比較考察

HACHもコミュニティAI「Hermes」も、NousResearchのオープンソースフレームワーク hermes-agent を共通基盤としている。
この前提を踏まえ、エージェント戦略の最適解を再考する。

01 — Common Foundation

共通基盤：NousResearch hermes-agent

☤ hermes-agent — "The agent that grows with you"

NousResearchが開発したMITライセンスの自己改善型AIエージェントフレームワーク。
HACHもコミュニティAI「Hermes」も、このフレームワークの上に構築される。

学習ループ

自己改善メカニズム

複雑なタスクの後に自律的にスキルを生成・改善。
FTS5セッション検索、LLM要約によるクロスセッション記憶。
Honcho による dialectic user modeling で、使うほどユーザーを深く理解。

マルチプラットフォーム

ゲートウェイ統合

Telegram / Discord / Slack / WhatsApp / Signal / CLI — 単一のゲートウェイプロセスから全プラットフォームへ接続。
音声メモのトランスクリプション、プラットフォーム横断の会話継続。

スケジューラ

自律実行 & 並列化

Cronスケジューラ内蔵。自然言語で日次レポート、週次監査などを設定。
サブエージェント生成による並列処理。
Docker / SSH / Modal / Daytona / Vercel Sandbox で実行。

重要な認識：hermes-agent はエージェントの「骨格」（学習ループ・ツール呼び出し・スケジューリング・マルチプラットフォーム接続）を提供するフレームワークであり、 その上に「何を目的としたエージェントを構築するか」がHACHと自社Hermesの分岐点となる。

04 — HACH vs Self-Built

HACHとの関係性の再定義

hermes-agent が共通基盤である以上、HACHは「同じフレームワークの別インスタンス（ビジネス特化）」と捉えるのが正確。競合ではなく、姉妹プロダクトの関係にある。

HACH = hermes-agent × ビジネスドメイン

ISM社が構築したインスタンス

hermes-agent の上に以下を実装：

・brain（判断基準）：自然言語で業務判断を調整
・業務データコネクタ：メール / カレンダー / 議事録の自動収集
・トリアージエンジン：赤/黄/青の優先度判定
・日次ダッシュボード：毎朝のレポート自動配信
・BYOCセキュリティ：御社AWS内でデータ完結

月額98,000円〜のマネージドサービスとして提供

Hermes = hermes-agent × コミュニティドメイン

自社で構築するインスタンス

hermes-agent の上に以下を実装：

・ネットワークグラフ：人物→プロジェクト→組織の関係性構築
・3つの自律エージェント：日時解決 / 矛盾修正 / 情報収集
・相乗効果検知：共鳴リンク / マッチングエージェント
・心理的安全性設計：自己開示レベル (Lv0〜Lv3)
・承認フロー：agent_proposals + オーナー承認UI

自社開発 + LLM API実費

05 — Strategic Options

3つの戦略オプション

Option A

HACH を OEM/連携して使う

判定：△ 条件付き可

hermes-agent 基盤が共通のため、HACHの業務情報収集・レポート機能を活用しつつ、コミュニティ特化レイヤー（グラフ・相乗効果）のみ自作する。

利点：情報収集・レポート・チャットBot基盤の開発が不要
課題：月額コスト、HACHのAPI仕様への依存、ISM社との連携調整が必要

Option B

hermes-agent で自社Hermesをフル構築

判定：⭕ 推奨

HACHと同じ hermes-agent フレームワークを直接利用し、コミュニティ特化のエージェントを構築。HACHが実現している機能（スケジュール実行、チャット連携、学習ループ）は hermes-agent のネイティブ機能で対応可能。

利点：月額コストなし、完全な制御権、コミュニティ特化要件を100%実装
課題：初期構築工数

Option C

両方のインスタンスを並走

判定：△ 将来的に検討

自社Hermes（コミュニティ分析）とHACH（事務局の業務効率化）を並走させ、それぞれ異なる目的で活用。

利点：各ドメインに最適化された運用
課題：2つのサービスの運用コスト、データの二重管理

06 — Recommended Architecture

推奨：Option B — hermes-agent で自社Hermesを構築

📋 結論：hermes-agent を直接利用して自社Hermesを構築する

HACHが実現している価値の大部分（チャット連携、スケジュール実行、学習ループ、マルチプラットフォーム対応）は、HACHの独自機能ではなくhermes-agent フレームワーク自体の機能である。 HACHの月額98,000円は、これらの共通基盤 + ビジネスドメイン特化（業務情報コネクタ・brain・BYOCセキュリティ）に対する対価であり、 コミュニティ分析という異なるドメインに対して同じ費用を払う必要はない。

  • hermes-agent は MIT ライセンス。無料で利用でき、ベンダーロックインなし。
  • LLMプロバイダに非依存。Nous Portal / OpenRouter / OpenAI / Gemini 等を自由に選択・切替可能。
  • HACHが「できること」の大半は hermes-agent が提供する。自社Hermesを構築する場合、HACHのようなマネージドサービスを通さずとも同等の基盤が手に入る。
  • コミュニティ特化要件（グラフ・相乗効果・心理的安全性）は自作が必須。HACHを導入してもこれらは追加開発が必要であり、工数の削減にならない。

🗺️ 実装ロードマップ

Phase 1（現行MVPの完成）：
現行のFastAPI + React ベースでMVPのグラフ可視化・エンティティ抽出を完成させる。

Phase 2（hermes-agent 統合）：
hermes-agent をインストールし、エージェント仕様書の3エージェント（日時解決・矛盾修正・情報収集）を hermes-agent のスキルおよびスケジュールタスクとして実装。 hermes-agent のゲートウェイを使って Slack / Discord 連携を実現。

Phase 3（自律化・発展）：
hermes-agent の学習ループを活用し、エージェントが運用を通じて判断基準を自己改善。 レポート生成エージェント、マッチングエージェントを追加。 Multi-Agent Orchestrator としてのHermes Core を確立。

Phase 4（HACH連携の再評価）：
コミュニティ運営の事務局業務（メール・議事録・タスク管理）の効率化ニーズが明確になった段階で、HACH導入による追加価値を再評価。 同じ hermes-agent 基盤であるため、データ連携やエージェント間通信の親和性は高い。
